# エージェント向け 開発・レビュー方針

このドキュメントは、GitHub Copilot / Gemini Code Assist / OpenAI Codex など
すべての実装者（AI エージェントおよび人間）が共有する方針です。プロジェクト固有の詳細は各エージェント
設定ファイル（CLAUDE.md / AGENTS.md / GEMINI.md / .github/copilot-instructions.md）
を参照してください。

---

## 実装前の整理

実装に着手する前に、以下を整理する。仕様が固まっていない状態で書き始めると、AI は不明点を推測で埋めて要求外の挙動を作り込みやすい。

- **変更目的**：何を・なぜ変えるか
- **変更対象**：どのファイル・層・責務に触れるか
- **影響範囲**：再描画・永続化・同期・他モジュールへの波及
- **検証方法**：どのテスト／手動確認で担保するか

不明点は埋めずに「未確認事項」として残す（PR 本文・コメント・Issue に明示する）。
この工程は着手前の整理であり、PR 本文に**事後**記載する「提供結果・最終的な変更・検証セクション」（[PR・コミットの作法](#prコミットの作法)）とは役割が異なる。

### 想定ケースの洗い出し（リスクモデリング）

上記の整理に続けて、想定すべき不正・異常・外部状態変化ケースを**一度すべて洗い出し**、対応するもの・見送るもの（理由付き）を分類する。手順とテンプレートの正本は [docs/agent-workflows/risk-modeling.md](agent-workflows/risk-modeling.md)。

これは PR レビューで初めて「〇〇の場合がある」と指摘される正当な設計レビューを、実装前へ前倒しするための工程である。

- **「全部ガードする」ではなく「一旦全部想定に上げて採否判断する」**。発生しないと判断する場合も理由を残す。
- GitHub正本・同期・IDB・Tiptap/ProseMirror 文書モデル・長文性能・UI失敗状態の観点を含める（GitHub 側の状態変化・ユーザーによる直接編集は通常運用上の入力として扱う）。
- **不正系・異常系テストの追加を優先候補**として検討する（下記「必須セルフレビュー項目」の「テスト」と整合）。見送る場合は理由を残す。
- pick-issue 経由なら実装計画に想定ケース表を含める。介さない作業でも [docs/agent-workflows/risk-modeling.md](agent-workflows/risk-modeling.md) を参照して洗い出す。

## コミット前セルフレビュー

実装完了後、コミット前に「レビュワー視点で自分の変更を確認する」工程を必須とする。
これは人間レビュー・AI レビューとは別の、**実装者自身による工程**である。
問題を発見したら修正し、修正後に再レビューする。

### 基本方針

- 実装完了直後にそのままコミットしない
- セルフレビューで発見した問題は必ず修正してからコミットする
- レビューで繰り返し指摘される問題は lint / test / CI に移行し、「毎回目視で見る」を削減する
- セルフレビュー段階は「今後どう自動防止するか」を考えるタイミングでもある

### セルフレビュー項目の改訂

セルフレビュー項目は固定ではない。実装者は以下を行ってよい。

- **追加**：今回のセルフレビューで気づいた観点を項目として追加提案する
- **削除**：実態に合わなくなった項目・冗長な項目の削除を提案する
- **lint / 自動化への移行**：目視確認から自動検出へ格上げできる項目は積極的に移行し、項目を削除する

このドキュメントはプロジェクトとともに育てるものであり、「書いてあるから機械的にチェックする」ためのものではない。
項目を改訂する場合は、このファイルへの変更を実装 PR に含めてよい。

### 必須セルフレビュー項目

**要求との一致**
- [ ] 要求された内容のみを変更しているか
- [ ] 要求外変更・「ついで修正」が混ざっていないか
- [ ] 既存仕様を勝手に変更していないか

**変更最小性**
- [ ] 修正範囲は最小限か
- [ ] 既存処理を再利用できているか
- [ ] 新しい helper / method / abstraction が本当に必要か
- [ ] 今回の修正のためだけに構造を壊していないか

**既存実装整合性**
- [ ] 現行実装の責務分担に沿っているか
- [ ] 同種処理と実装パターンが揃っているか
- [ ] 既存命名規則に沿っているか
- [ ] データ取得・状態更新・描画更新フローを壊していないか

**エッジケース**
- [ ] null / undefined / 空 / 0件 / 複数件
- [ ] 非同期失敗・ロック状態・未保存状態
- [ ] 再描画後・複数ダイアログ・selector 重複・同一ID重複

**テスト必須カテゴリ**

入力→出力が決定的な純粋ロジックのうち、出力が次のいずれかに影響するものは、同ディレクトリに `*.test.js`（vitest）を追加・更新する。仕様変更時に品質を均一担保するための回帰ネットであり、レビュアー指摘を待たずに実装と同じ PR で追加する。

- **文章クオリティ・テキスト変換**：ユーザーに見える本文・プレビュー・差分・保存テキストを生成/変換するもの（例: `markdown.js` / `writingRules.js` / `styleRules/` / `plainText.js` / `tiptap/textSerializer.js` / `tiptap/plainTextLoader.js` / `previewAnnotations.js` / `diffCore.js`）
- **セキュリティ境界**：XSS・パストラバーサル・不可視文字・不正入力を防ぐ判定/サニタイズ関数（例: `security/validate*` / `security/sanitize*` / `security/unicodeSafety.js` / `annotations.js` の `escapeHtml` / `escapeAttr` / `normalizeAnnotation`）

新規テストは対象の修正を revert すると fail する（red → green）こと。UI コンポーネント・IDB・ネットワーク等の副作用を伴う層はこのルールの対象外（E2E / 統合テスト側で担保する）。

**テスト**
- [ ] テストが対象を実際に検証しているか（例外が出ないだけ・名前だけになっていないか）
- [ ] **動作を変更した場合、影響を受ける既存テストが「正しい理由で」通過しているか確認したか**（振る舞いが変わったのに別の理由で偶然 pass し続けるテストは偽陽性になる）
- [ ] **新規テストはその修正を revert した状態で fail するか**（red → green を経ないテストは何も保証しない）
- [ ] コードを変えた後、テスト名・コメントが現状の動作と乖離していないか（「〜を truncate するため false」等の古い説明が残っていないか）
- [ ] selector が曖昧ではないか（グローバル ID より scoped locator を使う）
- [ ] 期待状態を明示的にアサートしているか
- [ ] RTL では `getByRole` / `getByLabelText` を優先し `getByText` を安易に使わない
- [ ] 存在確認は `toBeInTheDocument()`。`toBeDefined()` は DOM 検証にならない
- [ ] `fireEvent` より `userEvent`（@testing-library/user-event）を使う（将来移行目標）
- [ ] テスト名は「何を確認しているか」が読んでわかる日本語にする
- [ ] E2E: `page.reload()` や次アクションの前に IDB 非同期書き込みの完了を待っているか（`waitForSelector` 等）。await なしリロードはレースコンディションでフレークになる（PR#154・#133・#140 で繰り返し指摘）
- [ ] **貼り付け・クリップボード・キーボード入力の挙動を変更した場合、`e2e/editor/` または `e2e/security/` に Playwright E2E テストを追加したか**（入力経路は変更頻度が高く、単体テストのみでは回帰を検知しにくいため常態化する）

### agent-memory のライフサイクル操作を含む PR

記憶レコードの `status` が変わる操作（`promote` / `reject` / `retire` / `supersede`）と `purge`、および作業ブランチ外レコードの `revise` は、**判断の主体が人間**で、実行はエージェントでもよい（`docs/planning/agent-memory-design.md` §6.0）。この権限モデルの検査点はレビューだけなので、次を確認する:

- 対応する `Memory-Endorsement:` trailer がコミットに**存在するか**（`git log --format='%(trailers:key=Memory-Endorsement,valueonly)'`）。CLI が強制するのはフラグの指定までで、**コミットへの転記漏れは機械検出されない**
  - 確認には**必ず Git の trailer パーサ**（`%(trailers:key=…)`）を使う。`git log --grep='^Memory-Endorsement:'` は本文行にもマッチするため、trailer ブロックが無く本文に同じ文字列があるだけのコミットを通過させる（＝転記漏れの偽陰性。実測で確認済み）
- **逆方向も検査する**: trailer の各行に、対応するレコード変更（`status` / `supersedes` / `supersededBy` / `replaces` の変更、または purge の削除）が同じ PR の diff に**存在するか**。存在方向（遷移→trailer）だけ見ると、diff を伴わない endorse 記録（JSON 手編集後の no-op 実行や、回復用候補 trailer の不正な転記）が素通りする（#531 敵対的レビューで実証）
- endorse された内容が PR 上の人間の指示と整合するか（`--endorsed-by` の値は自己申告で検証できない。**記録の内容が本物かを判断できるのはレビュアーだけ**）
- 削除（`Memory-Purge:`）がある場合、理由が secret 混入であること（提案の無痕跡な取り下げに転用されていないこと）
- squash マージする場合、trailer を squash コミットへ引き継ぐこと（マージ実施者の責務）

### AI特有の確認項目

AI エージェントが起こしやすい事故を重点確認する。

- [ ] 実在しない helper / method / abstraction を前提にしていないか
- [ ] 現行実装を読まずに推測で実装していないか
- [ ] 仕様が不明な箇所を AI の推測で補完していないか（不明点は実装で勝手に決めず、PR 本文・コメント・Issue に「未確認事項」として明示する）
- [ ] 不要な wrapper / helper / abstraction を追加していないか
- [ ] 「安全そう」という理由だけで過剰ガードを追加していないか
- [ ] 要求外リファクタを混ぜていないか
- [ ] 既存責務を崩していないか
- [ ] コメントでしか理解できない複雑化をしていないか
- [ ] `eslint-disable` コメントで lint エラーを抑制していないか（抑制は根本修正の代替にならない。抑制が必要に見える場合は、コードの構造を変えて lint を通すか、ルール自体を設定ファイルで無効化するかを先に検討する）
- [ ] 振る舞いを変えた際に、影響するテストが「たまたま pass している」だけになっていないか確認したか（テストが green でも pass 理由が変わっていれば仕様の保護にならない）

### lint / 自動化観点

セルフレビューで問題を発見したら、修正と同時に以下を検討する。

- ESLint rule / custom lint rule で検出できないか
- Stylelint / static analysis で検出できないか
- テストケースとして追加できないか
- CI の fail 条件にできないか
- TypeScript の型で防止できないか

lint はレビューの代替ではなく、**レビューで毎回確認している単純作業を削減する**ために導入する。
自動検出に移行できた場合は、対応するセルフレビュー項目を削除してよい。

### コミット前チェックリスト

コミット直前に以下を必ず実行する。

```
[ ] git diff で変更内容を確認した
[ ] git diff --staged でステージング内容を確認した
[ ] 不要ファイル・debug code・コメントアウトがないことを確認した
[ ] npm run lint を実行してエラーがないことを確認した
[ ] npm run test を実行してテストが通ることを確認した
[ ] npm run build でビルドが通ることを確認した（構造変更時）
```

## PRレビュー対応

PRレビュアーからの指摘を受けて修正する際は、コード修正だけで完結させない。
指摘内容を起点に、セルフレビュー工程・自動化の改善も同時に行う。

### 対応の流れ

1. **コードを修正する**（通常の対応）
2. **「コミット前セルフレビューで防げたか」を考える**
   - 防げた → セルフレビュー項目に追加し、このドキュメントを更新する
   - 防げなかった（構造的な問題・仕様理解の問題など）→ 記録は不要だが原因を把握する
3. **自動検出できるか考える**
   - lint / static analysis / test / CI で検出できるなら対応し、セルフレビュー項目への追加は不要

### 判断フロー

```
レビュー指摘を受けた
  └─ コードを修正する
       └─ 今後も同じ問題が起きうるか？
            ├─ lint / test で自動検出できる → 自動化する（セルフレビュー項目への追加は不要）
            └─ 自動検出が難しい → セルフレビュー項目に追加 → このドキュメントを更新する
```

### 方針

- レビュー指摘への対応 PR に、このドキュメントの更新を含めてよい
- 「毎回レビュアーに指摘されて気づく」問題は自動化の候補。放置しない
- セルフレビュー項目が増えすぎた場合は、lint 化・自動化を優先してリスト圧縮する
- **レビューで挙げない（対象外の nit）**: ファイル名の平文言及のリンク化や、可読性に実害のない整形の好み等の**純ナビゲーション/整形 nit** は、correctness（観点別レビューの守備範囲）でも、良い lint / ゲート候補（「全言及をリンク化」は過剰リンクを強制する悪いルールになる）でもない中間層。挙げると実所見と同じレビュー枠・再レビュー周回を消費するため、**指摘しない**（人手/AI レビューで平文言及のリンク化を求めない）。既存リンクの切れ・アンカー不整合は `docs:links:check`（#426）が機械検出する。なお、**壊れたリンク・表崩れ・手順やコマンドの誤り等、可読性や正確性に実害のある docs の問題は nit ではなく、通常どおり指摘する**（本項の抑止対象は「実害のない好み」に限る）。

## 言語

- **コメント・レビュー・PR 説明はすべて日本語で書くこと。**
- 技術用語（API 名・ライブラリ名・変数名など）はそのまま英語で構わない。
- 英語のみのレビューコメントは不適切とみなす。

## コーディング規約

### 責務分離 (Single Responsibility)

- 1 コンポーネント / 1 モジュールが担う責務は 1 つ。
- サイドバーの各ツールは `*Mod.jsx` として自己完結させ、`SidebarBox.jsx` への
  登録のみで動作する設計を維持する。
- ビジネスロジックをコンポーネント内に書かない。カスタムフック (`src/hooks/`) や
  ライブラリ (`src/lib/`) に切り出す。

### DRY（重複排除）

- 同じロジックが 3 箇所以上に出現したら共通化を検討する。
- ただし「将来の再利用」を見越した先回り抽象化は禁止。
- 共通化・汎用 API を導入する場合は、**利用箇所・必要性・過剰設計でない根拠**を PR 本文に記載する（DRY の目的化・将来用の先回りでないことを明示する）。

### コメント

- **原則コメントなし。** 命名で意図が伝わるコードを書く。
- 例外：非自明な制約・既知バグの回避策・ProseMirror / TipTap 固有の落とし穴など
  「なぜそう書くか」が自明でない場合のみ 1 行で書く。
- 複数行コメントブロックや JSDoc 全体コメントは書かない。

### 型・バリデーション

- システム内部コードは信頼するが、システム境界（IndexedDB・外部 API・ユーザー入力）や不定になりうる状態には適切なガードを置く。
- 防御的 null チェックを境界以外に乱用しない。
- null / 型 / 存在チェック・フォールバックを足す前に、**呼び出し元とデータ生成元を確認**し、その値が本当に発生しうるかで必要性を判断する。
- 発生しない値に対する過剰防御や、意味のない初期値代入（使われない初期化・即上書きされる代入）を増やさない。線引きの詳細は [code-cleanup.md「defensive coding と過剰チェックの線引き」](maintenance/code-cleanup.md) を参照。

## PR・コミットの作法

### PR の単位（正本）

- **1 PR = 1 つの自己完結した提供結果・検証単位・ロールバック単位。**
- 機能・必要テスト・必要 docs・不要になった旧コードの削除は同一 PR に含めてよい。複数 issue を 1 PR で close してよく、1 issue を複数 PR で進めてもよい。
- PR を分割してよいのは、次のいずれかに該当する場合のみ:
  1. 独立してリリースできる（する必要がある）
  2. 独立して検証する必要がある
  3. 独立してロールバックする必要がある
  4. 外部依存・人間操作の時期が異なる
  5. セキュリティ / データ損失の境界が異なる
- ファイルや変更種別（docs・コード・テスト・清掃）の違いだけでは分割しない。内部の段階分離は commit で表現する。
- 5 条件に該当しないが分割が必要と考える場合（例: 自己完結だがレビュー困難な規模）は、勝手に分割せずユーザーに判断を仰ぐ（分割条件の不足として報告する）。
- 無関係な便乗修正は禁止（その PR の提供結果に含まれない変更を混ぜない）。

### issue の作成・close（承認フロー・正本）

issue の作成は禁止しない。ただし新規作成の前に次を行う:

1. 既存 issue を検索する
2. 現在の PR・既存 issue で処理できるか確認する
3. 新 issue が必要なら、次をユーザーへ提示して承認を得る: **タイトル / 問題 / 現 PR へ含めない理由 / 独立した完了条件 / 優先度**
4. 承認後、同じコンテキストを持ったエージェントが作成する

- ユーザーが明示的に issue 作成を依頼済みの場合は再確認不要。
- レビューの分類外所見・レビュー残件・見送り事項は自動起票せず、「issue 候補」として同フローでユーザーへ提示する。
- 既存 issue の close も同フローの対象（対象・理由を提示し承認後に close）。無承認で閉じてよいのは同一作業中に自分が誤作成した issue のみ。PR の `closes #N` による自動 close は、マージ操作（ユーザー）自体が承認にあたるため個別承認は不要。ただし 1 issue を複数 PR で進める場合は、issue を完了させる最終 PR のみ `closes` とし、途中 PR は `refs` を使う。
- 提示した候補（上記 5 項目）は `docs/planning/issue-candidates.md` に 1 行追記して記録する（セッションを跨ぐ場合は必須。会話のみの提示は揮発する。リポジトリ分離後の public 側には本ファイルが無いため、その場合は PR 本文「残る制約・判断」への記録で代替する）。承認がセッション終了後に届いた場合は、承認を確認した任意のエージェントが記録済みの内容を根拠に作成してよい。
- 作成する issue の本文構成: **問題 / 目的 / 現状 / 対応範囲 / 非目的 / 完了条件 / 依存関係**（調査ログ・会話履歴の転記はしない。詳細: [communication.md](ai/rules/communication.md)）。

### コミット・本文

- コミットメッセージは日本語可。変更の「なぜ」を簡潔に書く。
- PR 本文の基本構成: **提供結果（必要な理由を含む）/ 最終的な変更 / 検証セクション（完了条件・想定ケース・既存実装調査・証拠表・レビューループ記録 — コード変更 PR で必須の見出し名）/ 残る制約・判断 / closes・refs**（テンプレ・機械ゲート要件の正本は [create-pr.md](agent-workflows/create-pr.md)）。commit ごとの作業日誌・全レビューコメントの再掲・恒久 docs の複製は書かない。

## セキュリティレビュー（攻撃者目線）

**「自分が攻撃者だったらどう悪用するか」を考えながら以下を確認する。**

このプロジェクトの主な攻撃面（attack surface）:
- ユーザーが書いたMarkdownをHTMLに変換してブラウザで表示する（XSSリスク）
- GitHubトークンをブラウザ側で保持しCloudflare Worker経由でAPIを呼ぶ（トークン漏洩リスク）
- デバイス間でファイルを同期するWorkerエンドポイントが存在する（認証・パストラバーサルリスク）

### XSS

- [ ] ユーザー入力を HTML に埋め込む箇所で `escapeHtml()` / `escapeAttr()`（`src/lib/annotations.js`）が適用されているか
- [ ] `markdown.js` の変換パイプライン内でルビ・リンク・インラインコードの変換が実行される **前** に入力値がエスケープされているか
  （正規表現キャプチャグループ `$1` `$2` を直接 HTML に埋め込むとエスケープをバイパスできる）
- [ ] `dangerouslySetInnerHTML` の `__html` に渡す値はすべてサニタイズ済みか。意図的な使用には `eslint-disable` コメントと理由が書かれているか
- [ ] アノテーション（ハイライト・メモ）のユーザー入力が HTML に展開される経路がないか

### 認証・認可

- [ ] GitHub トークンがクライアントのログ・`console.log`・localStorage・コードコメントに平文で現れていないか
- [ ] Cloudflare Worker の各エンドポイントが、セッション Cookie なしで呼び出したとき 401 を返すか（認証バイパスがないか）
- [ ] OAuth の `scope` は最小権限になっているか（`repo` など広い scope は漏洩時の影響が大きい）

### パス・ID の検証

- [ ] ファイル ID やファイル名を使ってパスを構築する場合、UUID フォーマット検証などで `../`・絶対パスを含む ID を弾いているか
  （例: `files/${id}.json` に `id = "../manifest"` を渡すとパストラバーサルになる）
- [ ] URL パラメーターをそのまま GitHub API のパスに連結していないか

### CORS / CSRF

- [ ] `Access-Control-Allow-Credentials: true` を設定する場合、`Access-Control-Allow-Origin` に `*` を使っていないか
- [ ] 状態を変更する API（PUT / POST / DELETE）に CSRF トークンまたは `SameSite=Strict` Cookie が設定されているか
- [ ] クライアントの変更系 fetch は `workerFetchWithCSRF()` を使っているか（`workerFetch()` の変更系誤用がないか）。worker 側で `validateCSRFToken` を通しているか
      （`/github/*`（prefix 一括適用）・`/sync/*`（per-route 適用）・`/auth/authorize-repo` の変更系は CSRF token 検証を通る。⚠️ `POST /auth/logout`・`POST /auth/refresh` は CSRF/セッション検証なし（`/auth/*` の見直しは保留、詳細は [TRUST-BOUNDARY.md](security/TRUST-BOUNDARY.md)「攻撃ベクターと現状の対策」の CSRF 行）
- [ ] `Set-Cookie` の `SameSite` を `Lax`/`Strict` から緩める（`None` 等）変更を、CSRF 影響評価なしに行っていないか
- [ ] `ALLOWED_ORIGIN` が環境変数で正しく制限されているか（ワイルドカードになっていないか）

### GitHub 連携・EXTERNAL 入力の境界（詳細: [TRUST-BOUNDARY.md](security/TRUST-BOUNDARY.md) / [github-boundary.md](security/github-boundary.md)）

- [ ] GitHub 由来 URL（`html_url` / `avatar_url` / branch / repo 名）を `href` / `src` に使う時、`validateUrl()`（https/http のみ許可、`javascript:` / `data:` を拒否）を通しているか
- [ ] pull した EXTERNAL 本文・ファイル名を preview / エディタ / IDB に渡す前に `validatePulledContent()` を通しているか
- [ ] IDB / localStorage から読み出す新規レコードを利用前に normalizer（`normalizeFileRecords` / `normalizeFileMetadata` / `normalizeAnnotations` 等）で正規化しているか
- [ ] IDB 由来の `file.github`（owner/repo/branch/path）を GitHub API に渡す前に再認可（`authorizeRepo`）+ write path 検証しているか。worker 側でも再検証しているか（UI 検証だけで完結していないか）
- [ ] export / 将来の AI 送信に private metadata / secret / `file.github` を混入させていないか（allowlist 経由か）

### 入力検証

- [ ] ユーザー入力をリテラルとして `new RegExp()` に渡す箇所で `replace(/[.*+?^${}()|[\]\\]/g, '\\$&')` でエスケープしているか（正規表現モードで入力を受け付ける場合はエスケープ不要）
- [ ] 置換文字列の `$1` / `$&` などのバックリファレンスが意図しないデータ変換を起こさないか（`() => rep` 形式で literal 置換にする）
- [ ] 外部から受け取ったファイルサイズに制限を設けているか（DoS 対策）
- [ ] ユーザーが入力するファイル名・フォルダ名が長さ上限（`NAME_MAX`）でトリムされているか
- [ ] ファイル本文の保存前に `FILE_CONTENT_MAX` を超えていないかチェックしているか
- [ ] `innerHTML` / `insertAdjacentHTML` への直接代入がないか（ESLint `no-restricted-syntax` で検出）

### ストレージ・機密情報

- [ ] `IndexedDB` に保存する機密データ（トークン等）は XSS でアクセス可能であることを前提に、最小権限・最小保持期間で扱っているか
- [ ] 機密情報を `localStorage` に保存していないか（XSS で容易に読み出せる）
- [ ] Service Worker（PWA 対応時）がキャッシュする範囲に機密情報が含まれないか
- [ ] IndexedDB から読み込んだデータを使う前に null / undefined / 型のガードがあるか（特に配列・オブジェクトを期待する箇所）
- [ ] アノテーションの `selectedText` / `note` が長さ制限（`MAX_SELECTED_TEXT` / `MAX_NOTE_LENGTH`）以内に正規化されているか（`normalizeAnnotation()` を経由しているか）

### GitHub Actions / CI（サプライチェーン・issue #225）

`.github/workflows/*.yml` を変更する PR で確認する。方針の正本は [SUPPLY_CHAIN.md](SUPPLY_CHAIN.md)「public repo 化前の GitHub Actions hardening 方針」。

- [ ] ワークフローのトップレベルに `permissions: { contents: read }` があり、追加権限は必要な job 単位のみに限定されているか（不要な `write` / `id-token` 昇格がないか）
- [ ] 新規・変更された `uses:` が full-length commit SHA で pin され、末尾コメントに元タグが残っているか（third-party は必須）
- [ ] `pull_request_target` を使っていないか。使う場合、外部 PR コードの checkout/実行・Secrets 露出がないか、例外理由が docs に記載されているか
- [ ] CI の依存インストールが `npm ci`（lockfile 厳密一致）になっているか（`npm install` を使っていないか）
- [ ] `secrets.*` が `run:` に直接展開されず `env:` 経由か
- [ ] `container:` の image は tag＋digest で pin されており、更新時に両方が同時に差し替えられているか（digest 単独は tag 併記より GC 到達不能リスクが高い。片側だけの更新漏れがないか）
- [ ] `run:` 内でネットワークから取得するツール（`npm install -g npm@…` 等）は exact version で pin され、workflow 内1箇所の env（`<TOOL>_PIN`。npm は `NPM_PIN`）に集約され、job/step の `env:` で上書き（shadow）されていないか（根拠: [SUPPLY_CHAIN.md](SUPPLY_CHAIN.md)「外部参照の pin（Action / container image / 実行時取得 CLI）」）

## プロジェクト固有の注意事項

- **UI テキストのデフォルトはすべて日本語**（英語 UI は意図的な場合のみ）
- サイドバーモジュールの折り畳み動作：`ModuleWrapper` の `keepMounted` prop で
  タイマー系モジュール（Pomodoro / FlowTime）はアンマウント対象外とする
- `AppContext` は段階的に Zustand stores へ移行中。新しい状態は `src/stores/` に追加する
- `src/lib/db.js`（IndexedDB）が永続化の主体。`localStorage` 直接操作は避ける
- diff 計算は Web Worker（`src/workers/diffWorker.js`）で行う。重い処理をメインスレッドに持ち込まない
