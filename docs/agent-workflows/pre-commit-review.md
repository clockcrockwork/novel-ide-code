# コミット前セルフレビュー

> **Ground truth:** [docs/REVIEW_GUIDELINES.md](../REVIEW_GUIDELINES.md) / [CLAUDE.md](../../CLAUDE.md) / [INVARIANTS.md](../data-model/INVARIANTS.md) / 実装計画の想定ケース表
> **Entry gate:** レビュー対象スコープ（ブランチ差分 / 未コミット変更）を確定するまで完了報告に進まない
> **Required artifacts:** 観点別レビュー（[review-angles/README.md](review-angles/README.md)）・`/security-review` の所見と**所見ごとの裁定**（判断・理由・対応・証拠）、修正内容リスト、レビューループ記録（周回・系統ごと1行＋収束宣言）、完了報告
> **Verification gate:** `npm run lint` / `npm run test` / `npm run build`（構造変更時）。変更種別別は [docs/ai/rules/verification-gates.md](../ai/rules/verification-gates.md)
> **Anti-skip:** [docs/ai/README.md](../ai/README.md)「anti-skip rule」を参照（lint / test 失敗はレビュー以前の問題として即修正する）
> **Cost note:** 省略すると、規約違反・脆弱性・回帰がレビューや本番まで素通りする

コミット前にコード品質・セキュリティ・プロジェクト規約を検証し、問題があれば修正してから再レビューをループする。

## 手順

### 1. 変更内容の把握（共通 snapshot の生成）

```bash
npm run review:snapshot   # merge-base・完全 diff・修正 diff・変更ファイル分類を一括生成
```

観点によらない機械的処理（merge-base の確定・レビュー対象 diff の生成・変更ファイルの分類・高リスク領域の判定）は snapshot が担う。**各観点レビュアーがこの情報を毎回再構築しない**（生成物の一覧・置き場所・working tree / untracked の扱いは [review-angles/README.md](review-angles/README.md)「共通成果物（snapshot）」を正とする）。

script が使えない環境では従来どおり手動で把握する：

- `git diff` — 未ステージ変更
- `git diff --staged` — ステージング済み変更
- `git log --oneline $(git merge-base HEAD main)..HEAD` — ブランチ上のコミット一覧
- `git diff $(git merge-base HEAD main)..HEAD` — ブランチ全体の差分（main 比較）

**スコープ判定：**

| 状態 | レビュー対象 |
|------|-------------|
| ブランチ差分も未コミット変更もゼロ | 「レビュー対象の変更がありません」と報告して終了 |
| 未コミット変更のみあり（ブランチ差分ゼロ） | 未コミット変更のみをレビュー |
| ブランチ差分あり（未コミットあり/なし問わず） | main からのブランチ全体をレビュー対象とする |

コミット済みの変更も含めてレビューする理由：コミット後に `/pre-commit-review` を実行するケースでは `git diff` 系が空になりレビューがスキップされてしまうため。

### 2. lint・テスト実行

以下を順に実行する：

```bash
npm run lint
npm run test
npm run build  # 構造変更（import 追加・削除・ファイル移動等）を含む場合
```

エラーがあれば即座に修正する（lint エラー・テスト失敗はレビュー以前の問題）。

### 3. 観点別レビューを実行

[review-angles/README.md](review-angles/README.md) を正として Tier を判定し、対象系統の観点別レビュアー（`review-subtractive` / `review-riskmodel` / `review-spec` / `review-adversarial` / `review-quality` / `review-operability` / `review-cleanup` サブエージェント）を起動する。

- **Tier 判定（加算式。正本: [review-angles/README.md](review-angles/README.md)）**: 基礎 Tier = 高リスク領域・大規模 diff・新サブシステム = Full（7系統）／その他のコード変更 = Light（減算＋敵対的＋risk-model 検証＋コード品質＋清掃）。**実行可能設計文書**（スキーマ・状態遷移・CLI 契約・エージェントワークフロー等。パスの正本は README の加算規則）に触れる変更は基礎 Tier に関わらず**仕様＋運用性・状態遷移を加算**する。docs のみの PR は変更対象に応じて「設計文書」（減算＋仕様＋運用性＋清掃）／「Record」（`docs/agent-memory/records/` 配下。減算＋清掃）／「Docs」（その他の説明文書。清掃のみ）のいずれかを宣言する。判定結果と理由を1行残す
- **レビューモードと再探索トリガー**: 各系統に「所見確認 / 差分探索 / 全体再探索」のいずれかを割り当て、fresh 起動か継続かを決める。**2周目以降を一律「所見確認だけ」にしない**（修正で探索対象が変わった系統は新規探索を継続する）。判定は `npm run review:plan` が出す（正本は [review-angles/README.md](review-angles/README.md)「レビューモード」「観点別の再探索トリガー」「レビュアーの継続とリフレッシュ」）
- **実行設定**: 各レビュアーの model / effort / maxTurns は `.claude/agents/review-*.md` の frontmatter で明示済み（親セッション設定の無条件継承を避ける。正本: `scripts/agent/review-exec-config.js`）。`maxTurns` 到達等で未完了に終わったレビュアーは `未完了: incomplete（{未確認範囲}）` を返す契約で、**所見ゼロ（収束）として扱わない**
- 各レビュアーには**自系統の正本ファイルのみ**を読ませ、修正コンテキストを渡さない（アンカーの独立性維持。詳細は README の分離原則）
- **減算は他系統より先に起動する**（入口。「足さずに済まないか」を他系統の診断より前に問う）。**清掃は他系統が収束した最終1周のみ起動する**（修正ラウンドごとに回さない）
- 従来の `/code-review`（責務・DRY・潜在バグ・パフォーマンス等）の観点はコード品質系統（`review-quality`）と敵対的系統（`review-adversarial`）に吸収される。**`review-quality` は Light にも必須**（品質ゲートのフロア。理由は [review-angles/README.md](review-angles/README.md) の Tier 表脚注）。Full と Light の差は仕様・ビジネスロジック系統と運用性・状態遷移系統の有無
- **記憶適合（条件起動）**: 起動条件・起動判定行の書式・記録方法は [review-angles/README.md](review-angles/README.md)「条件起動系統」を正本とする（本ステップでは複製しない）

発見した問題はすべてステップ 6 で修正する。

### 4. /security-review を実行

観点別レビューの敵対的系統とは**併存で維持**する（security-review は脆弱性クラスの網羅チェック、敵対的系統は「この diff の修正自体をどう騙すか」のガード単位攻撃で、対象が異なる）。

`/security-review` スキルを実行し、現在のブランチの変更に対してセキュリティレビューを実施する。

- XSS（HTML 出力・dangerouslySetInnerHTML・escapeHtml 適用）
- 認証・認可（トークン漏洩・401 返却・OAuth スコープ）
- パス・ID 検証（パストラバーサル・UUID バリデーション）
- CORS/CSRF・入力検証・ストレージ・GitHub Actions hardening

発見した問題はすべてステップ 6 で修正する。

### 6. 問題の報告と修正（レビューループ）

問題が見つかった場合：

1. 問題を箇条書きで列挙する（{カテゴリ} — {ファイル:行} — {修正内容（理由）}）
2. 問題をすべて修正する。修正1件ごとに以下の2チェックを行う:
   - **同クラス全箇所適用**: ガード・修正を入れたら、同じ入力を扱う全箇所に適用したかを grep で確認し、検索クエリと結果を証跡として残す（過去に、同種の修正を1箇所にしか適用せず、同じ見落としで2回刺されたことがある）
   - **昇格判断の記載**: レビューループ記録の対応セル（または途中行の本文）に「回帰テスト追加 / lint・ゲート昇格 / 昇格なし（理由）」のいずれかを書く（instance の修正を class の修正に拡張できないか毎回問う）
3. **ステップ 1 に戻って再レビューする**（修正コミット自体が新たな問題を生む。過去に、1周目の修正が2周目の主要所見を複数件生んだことがある）

**収束条件と上限:**

- **収束 = 再レビューで新規所見ゼロ**（「新規所見」は [review-angles/finding-criteria.md](review-angles/finding-criteria.md) の計上基準を満たす所見。参考は数えない）（不在の証明ではなく観測）。「修正した」は収束ではない。修正後に必ずもう1周する。ただし**下記「review budget（自動探索の上限）」の枠を超えて自動探索を続けない** — 枠を使い切っても所見が残る場合は人間判断へ返す（ゼロを観測するまで自動で回し続けない）。
- **起動側の収束判定（同じ変更へ exploratory review を回し続けない）**: 次をすべて満たしたら収束とし、次の独立した completion unit へ進む — 当初の failure scenario が閉じた／完了条件を満たした／blocker 級の新規所見（[review-angles/finding-criteria.md](review-angles/finding-criteria.md)）が無い／修正が閉じる failure scenario を固定する regression test がある／変更種別の verification gate が green／残余が明示され後続 issue・候補へ送れる。1 系統あたりの起動は fresh 1 回＋所見確認 1 回まで（review budget の枠表が正本）で、残った所見は「残所見:」で列挙してユーザー判断へ返す。成功指標はレビュー周回数や所見数ではない
- **収束を判定する周回は、最終修正の作成者と独立したアンカーで行う**（最終独立レビュー。`review-plan.js` は起動義務として追跡しない — 起動単位が系統ではなく「1人が完全 diff を1回読む」ため。実施の判断は本節の枠に従う）。修正者自身の再スイープは「修正時に考慮したケース」の列挙にしかならず、考慮しなかった境界は定義上含まれない（過去に実証: 修正者のセルフ検証が複数周連続で所見ゼロだったのに対し、直後の外部レビューは毎回新たな実穴を検出した）。独立アンカー = 外部レビュー（Codex）・別モデル・修正コンテキストを持たないサブエージェントのいずれか（Gemini は退役済み。[second-opinion-review.md](second-opinion-review.md) §2）。ガード・分類器・正規表現に触れない修正のみの周回はセルフ検証で収束宣言してよい。
- **ガード種（正規表現・バリデーション・分類器）の修正には境界差分表を付ける**: 「この修正で新たに受理される入力クラス / 新たに拒否される入力クラス」を列挙し、各クラスに回帰テストまたは見送り理由を対応させる。修正が境界そのものを動かす以上、レビューの攻撃対象はこの差分である（差分表がないと、独立アンカーも全空間を再探索するしかなくなる）。`check-artifacts` ガードについては、境界差分の各入力クラスを表駆動スイープハーネス（[`tests/checkArtifactsSweep.test.js`](../../tests/checkArtifactsSweep.test.js)）への正例/負例の行追加として表現し、機械検証する（境界差分表と回帰テストを同一 artifact にする）。
- **所見は方向で分類して収束を判定する**: 偽陰性方向（ゲート素通り・検証回避）＝解消するまでマージ不可。偽陽性方向（正当な入力の誤ブロック）＝escape hatch（skip マーカー・人間の編集）が存在する前提で time-box し、残件は issue 候補として承認フロー（[REVIEW_GUIDELINES](../REVIEW_GUIDELINES.md#issue-の作成close承認フロー正本)）でユーザーへ提示したうえでマージしてよい。自然言語パターンの偽陽性境界は原理的に無限であり、ゼロまで追うループは停止しない。**この安全弁は枠を使い切った後も無条件に維持する**（偽陰性方向の所見は分類に関わらず解消するまでマージ不可）。

**review budget（自動探索の上限）:**

**正本は [review-angles/README.md](review-angles/README.md)「review budget（自動探索の上限）」**（枠の一覧・数え方・予算終了時の扱い・追加割当の手順）。ここでは収束手順に効く点だけを挙げる — 枠表を再掲しない（値を変えたときに片方だけが更新される）。

- **新規探索の上限は `review:plan` が適用して提案しない**（`applyBudget`）。実行者が毎回断る必要はない
- **`所見確認` は別枠**で、起動側が手動で回す。そこから新規探索へ自動で戻さない
- **`converged: false` のまま残る予算終了は、人間が判断するまで解けない。** 続行なら `escalate`、現状受容なら判断と理由を残す。**PR 番号が確定する前（本ワークフロー）は `docs/pr/PR-{番号}.md` がまだ存在しない** — 予算判断も所見の裁定と同じく作業中の一時情報として保持し、[create-pr.md](create-pr.md) の PR 番号確定後（ステップ4.5）に転記する。続行するなら `review-plan.js escalate --angles <系統> --reason "..."` で予算を割り当て、判断と理由を `docs/pr/PR-{番号}.md` に残す
- **finding intake は閉じない** — 閉じるのは自動探索であって、新しい所見の受け入れではない
- **最終独立レビュー**も同じ構造（fresh × `全体再探索` 1回。所見を修正した場合の確認は **`差分探索`** 1回で、`所見確認` ではない — 修正が別箇所を壊した場合を構造的に見逃すため）。machine の起動義務ではないので予算も手順側が持つ

予算を使い切っても所見が続く場合、次の6分類で判定して対応を決める（**同一アンカー内**での判定。個別修正で反復を続けない）。**これは収束の blocker ではなく、人間へ判断を返すための分類である**:

| 分類 | 対応 |
|---|---:|
| 反復・point-fix（同型の指摘が繰り返される） | 個別修正を停止し、根本原因を分析して**減算レビューへ戻る**（クラス単位で解決する）。減算が必須系統に含まれない Tier（Docs）では、根本原因分析の結果を清掃レビューの追加観点としてそのまま引き継ぐ（戻り先の系統が存在しないため） |
| 真に新規のブロッカー | **所見を出した系統のみ**再起動して収束まで続行する |
| 既存欠陥（本 PR 起因でない） | 現 PR に含めるかユーザー判断を仰ぐ |
| スコープ拡張 | issue 候補として承認フロー（[REVIEW_GUIDELINES](../REVIEW_GUIDELINES.md#issue-の作成close承認フロー正本)）へ |
| 重複・誤読・nit | 修正せず終了する |
| その他（上記5分類に当てはまらない） | 最も近い分類への強制分類はしない。提案分類名を添えてユーザー判断を仰ぐ（angle-*.md の「その他: {提案分類名}」と同じ思想） |

**再レビューは前周で所見を出した系統に加え、修正差分が探索対象を変えた系統も再起動する**（全系統の機械的な再実行はしないが、「所見を出した系統だけ」に狭めると修正が生んだ新しい欠陥を取りこぼす。判定は [review-angles/README.md](review-angles/README.md)「観点別の再探索トリガー」＝ `npm run review:plan` が出す。ただし**未解消所見を理由とした再起動は `review:plan` が提案しない** — 所見の有無は machine state に無いため、必要なら `review-plan.js escalate --angles ... --reason ...` で要求する〔理由の本文は state に保存されない。裁定は `docs/pr/PR-{番号}.md`〕）。予算を使い切って「反復・point-fix」以外に分類した場合も、残所見を列挙してユーザーに判断を返してよい（勝手に「コミット可能」と宣言しない）。

**予算を使い切ることは終了条件ではない**。外部レビューで新規ブロッカーが続く場合は、上の6分類で「反復する point-fix」と「真に新しい問題」を分類したうえで、Tier または探索強度を段階的に引き上げる（[review-angles/README.md](review-angles/README.md)「実効 Tier の更新」）。

**レビューループ記録（必須 artifact）:** 周回ごと・系統ごとに1行ずつ記録し、完了報告と PR 本文に含める（系統列の値は [review-angles/README.md](review-angles/README.md) の系統名。/security-review 等の系統外レビューは実行したレビュー名を書く）。セクション内・表の直前に **Tier 宣言行** `Tier: {宣言名}（判定理由1行）` を置く（宣言名の語彙と書式の正本は [review-angles/README.md](review-angles/README.md)「収束と記録」）。コード変更 PR、および実行可能設計文書・記憶レコード（`docs/agent-memory/records/`）・その他説明文書のみに触れる docs のみ PR（Tier: 設計文書 / Record / Docs のいずれか）では `npm run check:artifacts` がこのセクションの存在・収束宣言・**Tier 宣言×系統列の突き合わせ**（宣言 Tier に必須の系統行が揃っているか）を機械検査する（Record/Docs は後から追加）。docs のみ PR の Tier 宣言は該当する1つ（設計文書 / Record / Docs）。過剰トリガーを免除する場合は Tier 宣言行 `Tier: なし（説明・記録文書: 理由）` のみ記載しループ表は省略可。**最終行は閉じた受理文法で書く**: 新規所見セル＝数字のみ（`0` / `0件`。「なし」「0件（説明…）」等の自由記述は不可）、対応セル＝「収束」単独（上限超過時は「残所見: 内容」）。**予算終了で未確認範囲が残っている場合は `収束` で閉じない** — `review:plan` が `converged: false` を返す状態なので、対応セルに **「残所見: {系統}の未確認範囲（予算終了）」** と書く（所見が0件でも未確認範囲は残所見である）。所見の要旨・スイープ結果等の説明は途中行または周回セルに書く（機械検査は最終行のみが対象のため途中行は自由記述でよい）。

`check-artifacts` は必須セクションを H2（`##`）でのみ検出するため、PR 本文にはこの見出しレベルで貼る（`###` にすると「セクションがありません」で落ちる）。

**所見ごとの裁定の行き先（PR 番号が無い段階）:** 本ワークフローは PR 作成前に実行されるため、`docs/pr/PR-{番号}.md` はまだ作れない。**所見ごとの裁定（判断・理由・対応・証拠）は作業中の一時情報として保持し、[create-pr.md](create-pr.md) の PR 番号確定後（ステップ4.5）に `docs/pr/PR-{番号}.md` の `## 内部レビュー所見の裁定` へ転記し、追加コミットして push する**（転記の実行主体は PR を作成する側。**push まで行って初めて完了**。PR 番号が無い段階では実行できない）。`PR-pending.md` のような一時ファイルは作らない。**PR 作成前に中断した場合、コミット済みの修正は残るが所見ごとの裁定は失われる**（意味状態の完全復元は保証しない。境界の正本: `docs/planning/review-memory-boundary.md` §3「記録先の適用範囲」・§1(d)）。

**実効 Tier 宣言行**（省略可）: 外部レビュー由来の正当な新規所見等で系統が加算された場合、Tier 宣言行の直後に `実効Tier: {宣言名}（昇格理由1行）` を置く。`check:artifacts` は宣言があれば実効 Tier を必須系統の基準にし、初期 Tier より縮小する宣言を拒否する（正本: [review-angles/README.md](review-angles/README.md)「実効 Tier の更新」「収束と記録」）。

```markdown
## レビューループ記録

Tier: Light（通常コード変更・高リスク領域外）

| 周回 | 系統 | 新規所見 | 対応 |
|---|---|---|---|
| 1 | 減算 | 0件 | 対象なし |
| 1 | 敵対的 | 4件（stale ref / tooLarge 迂回 ほか） | 全修正＋回帰テスト追加 |
| 1 | risk-model 検証 | 1件（❌約束未実装） | 実装追加（昇格なし: 単発ケース） |
| 1 | コード品質 | 1件（既存ヘルパー再実装） | 全修正（昇格なし: 単発） |
| 2 | 敵対的＋risk-model 検証＋コード品質 | 2件（1周目修正起因） | 全修正＋lint 昇格 |
| 3 | 敵対的＋risk-model 検証＋コード品質 | 0件 | 収束 |
| 4 | 清掃 | 0件 | 収束 |
```

### 8. 自動化候補の提案

[docs/agent-workflows/systematize.md](systematize.md) に従い、今回のセッションで繰り返した操作を洗い出してスクリプト/ワークフロー化の候補を提示する。

候補がある場合のみ提示する。候補がない場合の「なし宣言」は不要（機械ゲートの対象外であり、該当ゼロの報告成果物を作らない）。
