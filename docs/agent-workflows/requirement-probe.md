# 非言語化要件・完了条件の洗い出し（requirement-probe）

> **Ground truth:** Issue 本文 / 依頼文 / [docs/MVP_PLAN.md](../MVP_PLAN.md) / [docs/ARCHITECTURE.md](../ARCHITECTURE.md) / 既存 UI の実挙動
> **Entry gate:** 完了条件チェックリスト（検証方法付き）を作り、曖昧点を質問リストまたは仮定として明文化するまで実装に進まない
> **Required artifacts:** 完了条件チェックリスト / 質問リストまたは仮定の明記（実装計画・作業メモ・PR本文に残す）
> **Verification gate:** ユーザーの承認、または「仮定のまま進む」ことの明記。実装系の検証は後続工程へ → [docs/ai/rules/verification-gates.md](../ai/rules/verification-gates.md)
> **Anti-skip:** [docs/ai/README.md](../ai/README.md)「anti-skip rule」を参照（「依頼文が明確なので洗い出し不要」は禁止。明確でも表を作り確認する）
> **Cost note:** 省略すると、レビューや受け入れ時に「そういう意味ではなかった」「エラー時にデータが消える」系の手戻りが発生する

実装開始前に、依頼文・issue に**書かれていない**要件と完了条件を洗い出し、「これがないと PASS できない」条件を検証方法付きの TODO にする工程。

**仕様を大きくする工程ではない。** 目的は暗黙の期待を明文化して合意可能にすることであり、機能を追加提案することではない。完了条件は検証可能な粒度に絞る（目安 5〜10 個）。超える場合も件数だけを理由に分割しない。分割を提案するのは [PR の単位の分割条件](../REVIEW_GUIDELINES.md#pr-の単位正本)（独立検証・独立ロールバック等）に該当する場合のみで、issue 化は承認フローでユーザーへ提示する。

plan モードでは完了条件チェックリストを plan 本文に含めることを推奨する（ExitPlanMode 時の plan ゲート `scripts/agent/hooks/check-plan-gates.js` は警告のみ。必須化されるのは想定ケース表・既存実装調査表）。

## 手順

### 1. 明示要件の列挙

issue 本文・依頼文から、明示的に要求されていることを箇条書きで列挙する。ここで解釈を加えない（書いてあることだけ）。

### 2. 非明示観点の走査

以下の観点表を**全項目**走査し、依頼文に書かれていないが期待されていそうな要件を「上げる」。該当しない観点も「該当なし」と判断した事実を残す（黙って飛ばさない）。

| 観点 | 確認すること |
|---|---|
| **UI / UX / 操作性** | 導線はどこから始まるか。キーボード操作・フォーカス。既存 UI のパターン（モーダル / サイドバー Mod / footer）との整合。UI テキストは日本語か |
| **データ保護** | 操作の途中失敗・リロード・タブ閉じでユーザーの本文・設定が消えないか。上書き前の既存データはどうなるか |
| **失敗時挙動** | エラーはユーザーに見えるか（空状態・成功扱いにならないか）。リトライ・ロールバックは必要か |
| **既存機能との相互作用** | 同期・diff・アノテーション・メタデータ等、隣接機能の前提を壊さないか |
| **状態の永続化** | どこまで永続化するか（IndexedDB / Zustand persist / 永続化しない）。復元時の挙動 |
| **境界・規模** | 空データ・初回起動・大量データ・長文でも成立するか |
| **MVP 段階** | [MVP_PLAN.md](../MVP_PLAN.md) の現段階の保証範囲に収まっているか。範囲外の期待が混ざっていないか |

不正入力・異常系・外部状態変化の詳細な洗い出しは本工程では**やらない**（後続の [risk-modeling.md](risk-modeling.md) の責務。重複させない）。

### 3. 完了条件の TODO 化

「これがないと PASS できない」条件だけを、**検証方法付き**のチェックリストにする。検証方法が書けない条件は完了条件として曖昧なので、書けるまで具体化するか落とす。

```md
## 完了条件

- [ ] {条件} — 検証方法: {ユニットテスト / E2E / 手動確認手順 / lint 等の具体}
- [ ] {条件} — 検証方法: {...}

## 完了条件に含めないもの
- {観点表で上げたが落としたもの} — 理由: {承認フローで issue 候補化 / MVP範囲外 / 依頼の意図と異なる 等}
```

このチェックリストは後続の [evidence-check.md](evidence-check.md) が証拠検証の入力として使う。ここに無い条件は完了判定の対象にならないため、「あったら良い」ではなく「無いと PASS できない」だけを書く。

### 4. 曖昧点の扱い

- 解釈が複数ありうる点は**質問リスト**としてユーザーに提示する（自己解決して実装に進まない）。
- 回答が得られない・待てない場合は、採用した仮定を「仮定: {内容}（未確認）」として完了条件の直下に明記して進む。仮定は PR 本文にも残す。

### 5. 引き継ぎ

完了条件チェックリスト・落とした項目・質問/仮定を実装計画（または作業メモ・PR 本文）に書き、[risk-modeling.md](risk-modeling.md) → 実装へ渡す。
