# PRレビュー対応

> **Ground truth:** [docs/REVIEW_GUIDELINES.md](../REVIEW_GUIDELINES.md)（規約・方針）/ `docs/pr/PR-{番号}.md`（過去対応ログ）/ PRコメント・差分
> **Entry gate:** PR番号を確定し、全コメントを収集・トリアージするまで実装に進まない（「❓ 要確認」はユーザー判断を得る）
> **Required artifacts:** トリアージ表（判断＋理由）、対応計画、`docs/pr/PR-{番号}.md` の対応履歴更新、レビュー振り返り（対象がある場合のみ。[review-retrospective.md](review-retrospective.md)）、各コメントへの返信
> **Verification gate:** 実装後に観点別レビュー（[review-angles/README.md](review-angles/README.md)）・`/security-review`、コミット前に [pre-commit-review.md](pre-commit-review.md)。[docs/ai/rules/verification-gates.md](../ai/rules/verification-gates.md)
> **Anti-skip:** [docs/ai/README.md](../ai/README.md)「anti-skip rule」を参照。判断理由を必ず1文で残し、見送りも記録する
> **Cost note:** 対応履歴を残さないと同一指摘のループが再発し、レビューコストが累積する

[docs/REVIEW_GUIDELINES.md](../REVIEW_GUIDELINES.md) の方針に従い、レビューコメントへの対応可否を判断・実装・記録する。
対応履歴は `docs/pr/PR-{番号}.md` に蓄積し、同一指摘のループを防ぐ。

## 手順

### 1. PR番号の確定

引数が与えられた場合はその番号を使用。なければ現在のブランチから取得する：

```bash
gh pr view --json number -q .number
```

取得できない場合はユーザーに番号を確認する。

### 2. PR差分レビュー

**起動前に新規探索枠の残りを確認する**（枠の定義はステップ3.5）。同じ PR で本ワークフローを2回目以降に実行する場合、ここで無条件に `/review` を起動すると2回目の fresh 探索になり、「枠を超えたら自動探索せず人間判断へ返す」に違反する。

| 残枠 | ステップ2の扱い |
|---|---|
| 新規探索枠が未消費（初回） | `/review` スキルを実行し、PR全体の差分を俯瞰する |
| 新規探索枠が消費済み（2回目以降） | **intake-only**。`/review` は起動せず、届いたコメントの収集（ステップ3）へ直行する。再探索が必要と判断した場合は、人間が継続予算を明示的に割り当ててから起動する |

出力はトリアージ判断（ステップ4）の補足情報として活用する。

### 3. コメント収集

以下を実行し、結果を構造化リストとして整理する：

```bash
# 全コメントをページネーション込みで取得（スクリプトが標準出力に JSON を返す）
bash scripts/gh/get-pr-comments.sh {PR番号}
# PR の差分も取得する
gh pr diff {PR番号}
```

スクリプトの出力 JSON をそのまま解釈し、各コメントを以下の形式で整理すること：
- コメントID（GitHub上のID）
- type（`inline` / `pr_level` / `review`）
- レビュアー名
- コメント本文（要旨）
- 対象ファイル・行番号（inline の場合）
- コメントが解決済みか（resolved）

すでに resolved になっているコメントは「対応済」として記録するだけでよい。

> **注意**: `get-pr-comments.sh` は REST API の制限により `resolved` を常に `false` で返す。resolved 判定が必要な場合は `gh pr view {PR番号} --json reviewThreads` で個別に確認すること。

### 3.5. 外部レビューの周回上限

上限の正本は [review-angles/README.md](review-angles/README.md)「review budget（自動探索の上限）」の枠表（値をここに写さない）。**新規探索の上限は `review:plan` が適用する**（`applyBudget`）ので実行者が毎回断る必要はない。`所見確認` と最終独立レビューは machine を経由しないため本ワークフローの実行者が数える。

**数えるのは review invocation であって、届いたコメントの本数・回数ではない。**

| 事象 | 枠を消費するか |
|---|---|
| 明示的に依頼した fresh レビュー（ステップ2の `/review`・外部レビュアーへの新規探索依頼） | **する**（新規探索1回） |
| 明示的に依頼した対象確認（修正が直ったか・修正差分に新しい欠陥がないかの1回） | **する**（確認1回） |
| push（synchronize）後に自然に届いた外部コメント（遅延コメント・自動レビュアーの投稿） | **しない** — finding intake であって invocation ではない |

これを分けないと、新規探索を1回しか依頼していないのに「遅延コメント＋自動レビュアーの投稿」だけで枠を使い切ったことになる（自動探索の終了と所見受け入れの終了は別物、という原則に反する）。

- **対応履歴のラウンド番号と枠の消費数は別物**。`docs/pr/PR-{番号}.md` の対応履歴に push ごとのラウンドを積むのは従来どおりでよい。枠として数えるのは上表の「する」だけで、両者を同じカウンタにしない
- **枠を使い切っても、正当な新規指摘（✅）が出続ける場合**: [pre-commit-review.md](pre-commit-review.md) の6分類表をそのまま適用する（「反復・point-fix」なら個別修正を止めて減算レビューへ、「真に新規のブロッカー」ならその指摘のみ対応を継続、等）。分類の実施記録はステップ4のトリアージ表に1行加える。**自動で新規探索へ戻さず、人間判断へ返す**
- **finding intake は閉じない**: 閉じるのは自動探索であって、新しい所見の受け入れではない（境界の正本: `docs/planning/review-memory-boundary.md` §4）

### 3.6. 外部新規所見による実効 Tier の更新

ステップ4で **✅（対応する）** と判断した外部所見のうち、**内部レビュー（観点別レビュー）では見つからなかった新規所見**は、初期 Tier のままでは同種の見逃しが続く証拠である。現在の PR のレビュー計画へ反映する（判定表の正本は [review-angles/README.md](review-angles/README.md)「実効 Tier の更新」）。

**`escalate` は残枠でゲートする。** `escalate` は次の `review:plan` で fresh の全体再探索を要求するため、**新規探索枠を消費済みの状態で無条件に実行すると §4 の「予算到達後は自動停止して人間へ返す」を迂回する**。

| 残枠 | 扱い |
|---|---|
| 新規探索枠が残っている | 下記のとおり `escalate` する |
| 新規探索枠が消費済み | **`escalate` しない**。所見は intake として裁定・修正のみ行い、再探索の要否を人間へ返す。**人間が継続予算を明示的に割り当てた場合にのみ** `escalate` を実行し、割り当ての理由を `docs/pr/PR-{番号}.md` に残す |

**所見そのものは machine state に入れない。** 「正当な新規所見か」「どの観点か」「どれだけ重大か」は本ステップの判断であり、その裁定は `docs/pr/PR-{番号}.md` に残す（ステップ8）。起動側へ渡すのは「やり直す系統」だけ（`--reason` は理由の言語化を要求するためのもので、**本文は state に保存されない**）:

```bash
# 初期 Tier 対象外なら実効 Tier へ加算され、fresh で全体再探索になる
node scripts/agent/review-plan.js escalate --angles operability --reason "外部レビューが手順の実行主体不在を検出（周回 {n}）"
# 複数観点をまたぐ所見は単一観点へ押し込まず、関連観点をすべて渡す
node scripts/agent/review-plan.js escalate --angles spec,adversarial --reason "…"
```

- **エスカレーションしない判断**（⏭️ 見送り・🔁 既判断・誤検知・任意改善・好み・既出所見の言い換え・PR 外で本 PR により悪化していないもの）は `escalate` せず、見送り理由を `docs/pr/PR-{番号}.md` に残す（Tier は動かさない）
- **高影響所見で基礎 Tier を Full へ上げる判断**は人間が行い、PR 本文の `実効Tier:` 宣言行に書く（`escalate` は系統の加算のみで基礎 Tier を上げない）
- 実効 Tier が上がった場合は、ステップ7の観点別レビューを**新しい実効 Tier で**実施し、PR 本文のレビューループ記録に `実効Tier:` 宣言行を追記する（`npm run check:artifacts` の検査対象）
- 実効 Tier は PR 内で縮小させない（加算した観点の確認が済んでも履歴上は保持する）

### 4. トリアージ判断

以下を読み込み、各コメントへの対応可否を判断する：

- [docs/REVIEW_GUIDELINES.md](../REVIEW_GUIDELINES.md)（コーディング規約・禁止事項・方針）
- `docs/pr/PR-{番号}.md`（過去対応ログ、存在する場合）
- ステップ2のレビュー結果、およびステップ3で取得したコメントとPR差分

各コメントに対して以下を返すこと：

| 判断 | 適用条件 |
|------|---------|
| ✅ 対応する | 規約違反・バグリスク・アクセシビリティ問題など、明確な問題がある |
| ⏭️ 見送り | REVIEW_GUIDELINES「過剰ガード禁止」「先回り抽象化禁止」等に抵触、または現状で問題が発生しない |
| 🔁 既判断 | 同一指摘への対応記録が `docs/pr/PR-{番号}.md`（存在する場合）または GitHub PR スレッドの返信にあり、**その判断理由の前提が現在も成立している**（ステップ8: **GitHub 由来の ✅/🔁 のみで内部所見も無い**ラウンドは `docs/pr/PR-{番号}.md` に記録されないため、その回の既判断は GitHub 返信が一次記録になる。内部所見を含むラウンドは同ファイルに記録される） |
| ❓ 要確認 | 仕様判断が必要で自律的に決定できない |

判断理由は必ず1文で付記すること。**⏭️ / 🔁 は理由を反証可能な前提として書く**——理由セルに `前提: … ／ 失効条件: …（任意）` を添え、判断が依存する外部状態を名指しする（書式はステップ8）。

**既判断（🔁）は結論ではなく「理由の前提」に紐づく。** 🔁 を貼る前に、記録された判断理由の前提が現在も成立するかを1回だけ確認する（再審理ではなく1文チェック）。前提が崩れていたら 🔁 は失効し、新規指摘として再トリアージ（✅ / ⏭️）し、`docs/pr/PR-{番号}.md` に「再分類」と理由の更新を明記する。前提を崩す要因は外部（レビュアーの新しい論拠）だけでなく、**本 PR の後続の修正そのもの**であることが多い（過去に実証: 一度 ⏭️ とした `残所見: なし` が、後続の受理文法の変更で前提〔真偽は evidence-check の担当〕が崩れ ✅ に再分類されたことがある）。この「前提の失効チェック」を毎回のフル再検討にすると 🔁 のループ防止機能が消えるため、確認は**1回・1文の成立確認に限定**する（一般原則は [skill-design-rubric.md](skill-design-rubric.md)）。後続修正による前提失効の系統的な洗い出しはステップ6.5「修正の波及セルフレビュー」で行う。

### 5. 対応計画の提示

ユーザーに以下を提示し、承認を得てから実装に進む：

```markdown
## 対応計画（PR #{番号}）

| # | レビュアー | コメント要旨 | 判断 | 理由 |
|---|-----------|------------|------|------|
| 1 | Copilot   | ...        | ✅   | ...  |
| 2 | Codex     | ...        | ⏭️  | ...  |
```

「❓ 要確認」が含まれる場合はユーザーの判断を求めてから続行する。

### 6. 実装

「✅ 対応する」と判断したコメントを順に実装する。

- 1コメント = 1つの変更にまとめる（複数コメントを1コミットにまとめてよい）
- **同クラス全箇所適用**: ガード・修正を入れたら、同じ入力を扱う全箇所に適用したかを grep で確認し、検索クエリと結果を証跡として残す（過去に、同一の見落としで2回刺されたことがある。詳細は [pre-commit-review.md](pre-commit-review.md) ステップ6）
- 実装後に影響範囲を再確認し、意図しない変更が混ざっていないか確認する（詳細はステップ6.5）
- [docs/REVIEW_GUIDELINES.md](../REVIEW_GUIDELINES.md) の「必須セルフレビュー項目」を念頭に置く

### 6.5. 修正の波及セルフレビュー（過去判断の失効チェック）

⏭️ / 🔁 判断は結論ではなく**理由の前提に紐づく失効しうる約束**であり（ステップ4）、その前提を崩す要因は外部（レビュアーの新論拠）だけでなく**本 PR の後続修正そのもの**であることが多い。ステップ4のトリアージを **diff → 過去判断の方向で後ろ向きに再適用**する軽量チェック（[evidence-check.md](evidence-check.md) 手順4のドリフト監査＝前向きと対）。

- **トリガー**: ガード種の修正——**境界を動かす修正**をランドさせたとき。判定基準は新造せず [pre-commit-review.md](pre-commit-review.md) ステップ6 の「ガード種（正規表現・バリデーション・分類器）＝境界差分表が生じる修正」を正本参照する。境界差分表が生じない修正（docs / prose のみ等）は本ステップ自体が対象外（宣言も不要）。
- **手順**: その修正で境界が動いた結果、前提が崩れる過去の ⏭️ / 🔁 判断を列挙し、各前提が今も成立するか1文で確認する（フル再審理はしない＝過剰化防止）。列挙元は `docs/pr/PR-{番号}.md`（存在する場合）**に加えて GitHub PR スレッドの過去返信**（ステップ8の条件付き作成により、**GitHub 由来の ✅/🔁 のみで内部所見も無い**ラウンドは同ファイルに記録されず GitHub 返信が一次記録になるため）。崩れていれば 🔁 / ⏭️ は失効し、新規指摘として再トリアージ（✅ / ⏭️）して理由の前提を更新する（ステップ4の失効フローへ接続。GitHub 返信が一次記録だった判断が失効した場合は、更新後の判断を新規コメント返信で明示する）。
- **該当なしの場合**: 列挙した過去判断の前提がすべて成立している（または影響する過去判断がない）場合、宣言・記録は不要（機械ゲートの対象外。該当ゼロの報告成果物を作らない）。

### 7. コード品質・セキュリティ確認

実装後、コミット前に以下を順に実行する：

1. **観点別レビュー**（[review-angles/README.md](review-angles/README.md) を正とする）— `npm run review:snapshot` → `npm run review:plan` で Tier（加算式: 実行可能設計文書に触れる変更は仕様＋運用性・状態遷移を加算）・実効 Tier・起動系統・レビューモード（所見確認／差分探索／全体再探索）・fresh/継続を確定し、対象系統のレビュアー（`review-subtractive` / `review-riskmodel` / `review-spec` / `review-adversarial` / `review-quality` / `review-operability` / `review-cleanup`）を起動する。**減算は先に起動し、清掃は他系統が収束した最終1周のみ起動する**。ステップ3.6 で実効 Tier が上がっている場合は加算された系統も対象に含める。記憶適合（条件起動）の起動条件・記録方法は [review-angles/README.md](review-angles/README.md)「条件起動系統」を正本とする。指摘があれば修正する。
2. `/security-review` — セキュリティ脆弱性（XSS・インジェクション・情報漏洩等）を確認。指摘があれば修正する（敵対的系統と併存で維持）。

いずれも**新規所見ゼロを観測するまで**修正と再実行を行い、周回・系統ごとに1行の「レビューループ記録」を残す（ただし [review-angles/README.md](review-angles/README.md)「review budget」の枠を超えて自動で新規探索を続けず、人間判断へ返す）（収束条件・周回上限・表フォーマット（系統列込み）は [pre-commit-review.md](pre-commit-review.md) ステップ6 を正とする。ステップ9 のループと合算して1つの表でよい）。

> **所見の由来を問わず、裁定はステップ8の `docs/pr/PR-{番号}.md` へ記録する。** 内部所見だけ GitHub スレッドという一次記録を持たないため、記録先を外すと恒久記録から消える（境界の正本: `docs/planning/review-memory-boundary.md` §3）。
>
> **ただし置き場所は由来で分ける。** 外部レビュー由来は `## 対応履歴` の表へ、**観点別レビュー・`/security-review` の内部所見は `## 内部レビュー所見の裁定` セクションへ**（移行期は非表形式。`scripts/analyze-pr-history.js` が `|` 始まりの行をファイル全体で走査し、外部レビュー指標の母集団へ混入するため）。項目・判断記号はどちらも同じものを使う。
>
> 記録するのは**所見ごとの判断・理由・対応・証拠**だけ。レビュアーの生出力・所見ゼロの周回・起動の経緯は転記しない（作業日誌にしない）。
>
> **唯一の例外: 最終独立レビューは所見ゼロでも実施記録を残す。** machine が起動義務として追跡しなくなったため（[review-angles/README.md](review-angles/README.md) 手順8）、記録が無いと「実施した」と「省略した」を区別できない。実施した事実・対象 HEAD・結果（所見ゼロ）の3点だけを1行で残す。

### 7.5. レビュー振り返り（外部レビュー起因の根本原因分析）

ステップ7の収束（新規所見ゼロ）後に、[review-retrospective.md](review-retrospective.md) を正本として実行する。

- **対象**: GitHub 上のレビューコメント（外部レビュアー・別モデル・別セッション）で初めて発見された正当な新規指摘（✅）のうち、バグ・回帰・セキュリティ等の影響と再発可能性・内部捕捉可能性があるもの。分析対象の入力は `## 対応履歴` の表（＝外部レビュー由来）に限る。内部の観点別レビュー所見は別セクション（`## 内部レビュー所見の裁定`）にあり、振り返りの目的は「内部で捕捉できなかった理由の分析」なので分析対象ではない — 内部所見は分析の**参照側**として使う。対象選別の判定表は正本を参照。
- **実施者**: 実装・修正コンテキストを持たないサブエージェント `review-retrospective`（`.claude/agents/review-retrospective.md`）を起動し、発生原因・内部検出漏れ原因（本来の捕捉工程と通過理由）・再発防止を分析させる。**当該ラウンドの確定済みトリアージ表（ステップ4〜5の結果。この時点ではまだファイル未反映）はメインセッションが起動時に入力として渡す**（渡さないと、サブエージェントは `docs/pr/PR-{番号}.md` に過去ラウンドしか見つけられない）。分析結果はステップ8で `docs/pr/PR-{番号}.md` の `## レビュー振り返り` セクションへ転記する。
- **該当なしの場合**: 対象が0件なら宣言・記録は不要（機械ゲートの対象外。該当ゼロの報告成果物を作らない）。

### 8. docs/pr/PR-{番号}.md の更新（条件付き作成）

条件付き作成とした経緯: `docs/planning/review-system-phase2-plan.md`。このファイルは**恒久価値のある内容が発生した場合のみ**作成・追記する。全コメントの対応履歴を毎回転記する「作業日誌」ではない（一次記録は GitHub PR スレッド。ステップ11 の返信がそれを担う）。

- **作成・追記する場合**: このラウンドに ① 前提付き見送り判断（⏭️。ステップ6.5 の失効チェックの入力になる）、② レビュー振り返り（対象ありの場合。ステップ7.5）、③ **観点別レビュー・`/security-review` の所見**（GitHub スレッドという一次記録を持たないため、ここが唯一の恒久記録になる）、または ④ **最終独立レビューの実施**（所見ゼロでも記録する。上記の例外）のいずれかが含まれる
- **作成・追記しない場合**: このラウンドが GitHub コメント由来の ✅（対応する）と 🔁（既判断）のみで、新規の ⏭️ も振り返り対象も内部所見もない。対応・既判断はステップ11 の GitHub 返信で足りる
- 既存ファイル（本ルール導入前の全履歴転記を含む）は削除しない（`analyze-pr-history.js` の入力・過去 ⏭️ の参照先として残す）

ファイルが存在しない場合は新規作成、存在する場合は該当セクションに追記する（**外部レビュー由来は `## 対応履歴`、内部所見は `## 内部レビュー所見の裁定`**）。

**フォーマット（新規作成時）：**

```markdown
# PR #{番号} レビュー対応ログ

## PR概要
{PRタイトルと対象Issue}

---

## 対応履歴

### {YYYY-MM-DD} | commit: `{コミットハッシュ（実装後に記入）}`

波及影響: {ガード種修正で過去判断の前提が崩れた場合のみ記載（※それ以外は行ごと削除）}

| # | レビュアー | コメント要旨 | 判断 | 理由 | 対応内容 |
|---|-----------|------------|------|------|---------|
| 1 | ...       | ...        | ✅   | ...  | ファイル:行番号 に〇〇を追加 |
| 2 | ...       | ...        | ⏭️  | 前提: {X が Y である限り不要} ／ 失効条件: {X が変わったら見直す} | - |
| 3 | ...       | ...        | 🔁  | **既判断: 上記 #{項番} 参照**（前提成立を確認済み） | - |

## 内部レビュー所見の裁定

<!-- 観点別レビュー・/security-review の所見。表形式にしない（analyze-pr-history.js は
     `|` 始まりの行をファイル全体で走査し、外部レビュー指標の母集団へ混入するため）。
     項目・判断記号は対応履歴と同じ。対象が無いラウンドでは節ごと省略してよい -->

### {系統} — {新規探索 / 所見確認}{n}回目（snapshot `xxxx`）

- **#{n} {所見の要旨}** — 判断: ✅ ／ 理由: {1文} ／ 対応: {何をしたか} ／ 証拠: `file:行`

## レビュー振り返り

<!-- 対象がある場合のみこのセクションを作る（対象0件なら省略）。書式の正本: docs/agent-workflows/review-retrospective.md（表は位置を問わずパーサに取り込まれるため、本セクションでは表と「### 日付」見出しを使わない） -->

- 実施日: {YYYY-MM-DD} / commit: `{ハッシュ}` / 実施者: {サブエージェント/モデル}
- レビュー振り返り: 対象あり（{n}件）＋所見ブロック
```

**理由列の書式（⏭️ / 🔁）：** ⏭️ は `前提: … ／ 失効条件: …（任意）` を書き、判断が依存する外部状態を名指しする（結論だけの理由は後続修正で前提が崩れても追跡できない）。🔁 は `**既判断: 上記 #{項番} 参照**` に加え、参照先の前提が今も成立することを1文で確認した旨を残す（ステップ4）。

**追記時（2回目以降）：**

外部レビュー由来は前回の表の下に新しい `### {日付} | commit: ...` セクションを追加する。**内部所見は `## 内部レビュー所見の裁定` 配下へ、系統・ラウンド単位の見出しで追記する**（対応履歴側の表に混ぜない）。**セクション順は `## 対応履歴` → `## 内部レビュー所見の裁定` → `## レビュー振り返り` を維持する**——外部ラウンドの新しい表は `## 対応履歴` セクション内の末尾（次の H2 の直前）に挿入し、レビュー振り返りの2回目以降は `## レビュー振り返り` セクション内に実施日行から追記する（ラウンドの表が振り返りセクション配下に入り込むと、同セクションの「表・日付見出し不使用」制約が崩れる）。
「🔁 既判断」の場合は `**既判断: 上記 #{項番} 参照**` のように同一ドキュメント内を参照する。前提欄のない**旧記録**（本ルール導入前の ⏭️ / 🔁）を 🔁 で再利用する場合は、貼る前に前提成立を1文で確認し、確認結果（＋必要なら前提）をその行に追記する（旧結論の無条件保護を防ぐ。一括遡及改訂はしない）。

### 9. コミット前セルフレビュー

[docs/agent-workflows/pre-commit-review.md](pre-commit-review.md) に従う。新規所見ゼロで収束するまで修正と再実行を繰り返し、レビューループ記録を更新する（PR 本文の「レビューループ記録」セクションに追記する。`npm run check:artifacts` の検査対象）。

### 10. コミット

```bash
git add .
git commit -m "fix(#{PR番号}): {対応したコメントの要旨}"
COMMIT_HASH=$(git rev-parse --short HEAD)
```

**`docs/pr/PR-{番号}.md` を作成・追記したラウンドのみ**、コミット後にコミットハッシュ欄を `$COMMIT_HASH` で更新する（ステップ8の条件で作成しなかったラウンドはこの操作自体が対象外）。

### 11. GitHubコメントへの返信

対応したコメントと見送ったコメントそれぞれに返信する。返信文中の `docs/pr/PR-{番号}.md` への言及は、**そのラウンドで同ファイルを作成・追記した場合のみ**含める（ステップ8で作成しなかったラウンドは GitHub スレッドの本返信そのものが一次記録になる）。

**対応済みの場合（PR-{番号}.md 作成・追記あり）：**
```markdown
対応しました（commit: {ハッシュ短縮形}）。
詳細は `docs/pr/PR-{番号}.md` を参照してください。
```

**対応済みの場合（PR-{番号}.md 作成・追記なし）：**
```markdown
対応しました（commit: {ハッシュ短縮形}）。
```

**見送りの場合：** ⏭️ は前提付き判断のためステップ8で必ず記録対象になる。
```markdown
見送ります。理由：{理由}。
`docs/pr/PR-{番号}.md` に記録しました。
```

**既判断（ループ）の場合：** 参照先が `docs/pr/PR-{番号}.md` にある場合と GitHub スレッドの過去返信にある場合とで文言を分ける（ステップ4「🔁 既判断」）。
```markdown
前回対応時に同一の指摘を検討し、見送りと判断しています（`docs/pr/PR-{番号}.md` #{行番号} 参照）。
判断を変更すべき新たな理由があればお知らせください。
```
```markdown
前回対応時に同一の指摘を検討し、見送りと判断しています（{日付}のコメントへの返信を参照）。
判断を変更すべき新たな理由があればお知らせください。
```

返信には以下のスクリプトを使用する：

```bash
# インラインコメントへの返信（第4引数にPR番号が必須）
bash scripts/gh/post-reply.sh inline {comment_id} "{返信内容}" {PR番号}

# PRレベルコメントへの返信（第2引数はPR番号）
bash scripts/gh/post-reply.sh pr_level {PR番号} "{返信内容}"
```

### 11.5. レビュースレッドの resolve（返信後・CI起動前）

ステップ11 で返信したインラインレビューコメントのスレッドを resolve する。**返信すること自体は
resolve ではない**（GitHub 上、返信済みでも `is_resolved: false` のまま残る。[ci-run.md](../ai/rules/ci-run.md)
「merge 前必須確認」の正本チェックリスト自体は未解決スレッドを判定項目に含まないが、resolve しない
まま放置すると GitHub 上「対応未了」に見え続けるため、返信と resolve を一体の工程にする）。

- 対象は**このラウンドで返信したスレッド**に加え、`isResolved: false` のスレッドのうち
  **スレッド内最後のコメントがこのエージェント（このセッション）自身の返信であるもの**
  （前回の実行が返信後・resolve 前に中断した場合等）。最後のコメントがレビュアーのもの
  （再質問・追加指摘）であれば「返信待ち」であり対象外 — 機械的に判定できない「対応中かどうか」
  を推測しない。
- `mcp__github__resolve_review_thread` で該当スレッドを resolve する。**thread ID はステップ3の
  `get-pr-comments.sh` の出力からは取得できない**（同スクリプトが返すのは REST の数値コメント ID
  であり、`resolve_review_thread` が要求する GraphQL のスレッド node ID とは別物）。`pull_request_read`
  の `get_review_comments` を実行し、そこで返る thread ID を使う（`isResolved` も返るため、上記
  「未 resolve のまま残っているスレッド」の特定にもこの呼び出しを使う）。
- **resolve は「対応済みとして応答した」という GitHub 上の表示状態であり、「合意した」という判断
  そのものの記録ではない**。⏭️（見送り）判断の恒久記録は `docs/pr/PR-{番号}.md`（ステップ8）と
  GitHub 返信本文が担う。resolve してスレッドが折りたたまれても、この記録は残る。
- 見送り（⏭️）判断の返信も、返信内容自体がその指摘への応答として完結していれば resolve してよい。
- resolve 対象か判断に迷うスレッド（レビュアーからの再質問を要する等）は resolve せず残す。

### 11.6. CI の起動（レビュー収束時のみ）

必要なレビュー系統が収束し、これ以上の修正 push が無い見込みになったら、**最新 HEAD に対して
CI を明示起動する**（`ci.yml` は push では起動しない）。起動方法・状態遷移・再実行条件は
[docs/ai/rules/ci-run.md](../ai/rules/ci-run.md) を正本とする。

収束していない段階では起動しない（中間 HEAD の重複検証が枠を消費する）。起動後に修正 push が
発生した場合は、その commit は未検証なので再度起動する。

**merge を実行・提案する場合**は、CI 成功を確認しただけで進めない。
[docs/ai/rules/ci-run.md](../ai/rules/ci-run.md)「private 期間: エージェントの merge 前必須確認」
（正本）の全項目を毎回確認してから判断する。private repository では required status checks に
拘束力が無いため、この確認はエージェント側の運用義務として行う。
