# 完了証拠の検証とスコープドリフト監査（evidence-check）

> **Ground truth:** 完了条件チェックリスト（[requirement-probe.md](requirement-probe.md)）/ 想定ケース表（[risk-modeling.md](risk-modeling.md)）/ 実際の diff・テストコード・コマンド実行結果
> **Entry gate:** 検証対象の宣言（完了条件・TODO・PR本文のチェック項目）をすべて収集するまで PASS 判定を出さない
> **Required artifacts:** 証拠表（宣言 × 証拠の所在 × 判定）。PR 本文または作業メモに残す
> **Verification gate:** `npm run check:artifacts`（機械的下限ゲート）を通過し、全項目が ✅（証拠あり）または明示的な差し戻し（❌ / ⚠️）に分類されている → [docs/ai/rules/verification-gates.md](../ai/rules/verification-gates.md)
> **Anti-skip:** [docs/ai/README.md](../ai/README.md)「anti-skip rule」を参照。追加禁止事由: 「完了と書いてあるので完了」「実装者が確認済みと言っているので確認済み」
> **Cost note:** 省略すると、未実施項目がチェック済みとして PR に載り、レビュー後・マージ後に「実はやっていなかった」が発覚する

「やった」という**主張**と、やったことを示す**証拠**を突き合わせる工程。宣言だけの完了をつぶし、途中で増えた要求外の変更を検出する。

実行タイミングは 2 つ：

- **完了時（必須）**: 実装完了の宣言後、create-pr の前。
- **実装中の中間実行**: 手順 4（ドリフト監査）のみを実行し、脇道・TODO 不一致を早期に戻す。以下のいずれかに該当したら**必須**（「推奨」ではない。無言スキップは anti-skip 違反）:
  - 外部レビュー・セルフレビューの差し戻しで**修正コミットを積んだ後**（修正が要求外変更を持ち込みやすい）
  - 実装が**複数コミットにまたがった時点**（初回コミット時の完了条件と現状の diff が乖離し始める）
  - どちらにも該当せず実施しない場合は、完了時の証拠表に「中間監査: 対象外（単一コミット・差し戻しなし）」と1行残す

実装した本人（同一セッション）ではなく、**別モデルまたは実装コンテキストを持たない別セッション・サブエージェント**で実行することを推奨する（[subagent-roles.md](subagent-roles.md) 原則3）。

## 手順

### 1. 宣言の収集

検証対象となる「完了したことになっている項目」をすべて集める：

- requirement-probe の完了条件チェックリスト
- risk-modeling の想定ケース表の「今回対応するもの」と「不正系テスト計画」
- PR 本文・作業メモ・コミットメッセージ内のチェックリストと完了主張
- pre-commit-review の完了報告（lint / test / build の実行主張）

### 2. 証拠の判定基準

各宣言に対して、以下のいずれかの**検証可能な証拠**を特定する：

| 証拠の種類 | 例 |
|---|---|
| diff 内の該当実装 | `{ファイル}:{行}` を指せること。「どこかで対応した」は不可 |
| テストコード + 実行結果 | 該当ケースを検証するテストが diff に存在し、`npm run test` が通っている |
| コマンド実行結果 | lint / test / build / security 系 script を**このセッションまたは記録上で実際に実行した**出力 |
| 手動確認の記録 | 確認手順と結果が作業メモ・PR 本文に具体的に書かれている（「動作確認済み」の一言は不可） |

**証拠にならないもの**: 完了主張そのもの・実装者の「確認済み」という発言・「既存コードと同様なので問題ない」。

### 3. 証拠表の作成

```md
## 証拠表

| 宣言 | 証拠 | 判定 | 前提 |
|---|---|---|---|
| {完了条件・TODO} | {ファイル:行 / テスト名 / 実行コマンドと結果} | ✅ / ⚠️ / ❌ | {判定が依存する外部状態。⏭️ 相当は「X が Y である限り」} |
```

- ✅ **証拠あり** — 検証可能な証拠を特定できた
- ⚠️ **証拠不十分** — 実装らしきものはあるが検証されていない（テストなし・実行記録なし）→ 差し戻し
- ❌ **未実施** — 宣言に対応する実体がない → チェックを外して未完了 TODO に戻す

**「前提」列は任意情報列**（機械ゲート `check-artifacts` の必須検査対象ではない。列を足しても既存の列検出は壊れないが、非空も強制されない）。判定が「今のところ問題ない／今回対応しない」に依存する場合、その依存先の外部状態を前提として名指しする。前提が後続の修正で崩れていないかは [review-pr.md](review-pr.md) ステップ6.5「修正の波及セルフレビュー」が後ろ向きに監査する（手順4は前向き監査。両者の対関係は手順4末尾を参照）。前提列の**中身の真偽**は floor の範囲外で、cross-model の本工程が担保する（必須化するなら別 issue で受理文法を定義してから）。

疑わしい場合は自分で再実行して確かめる（`npm run lint` / `npm run test` 等は実行して確認してよい）。再実行できない主張（手動 UI 確認等）は ⚠️ とし、確認手順の記録を要求する。

### 4. スコープドリフト監査

証拠表と並行して、宣言と実態の**逆方向**の不一致を確認する：

- [ ] チェック済み TODO で実態が伴わないものはないか（→ 手順3 の ❌）
- [ ] 依頼・完了条件に**ない**変更が diff に混入していないか（途中で増えた機能・要求外のリファクタ・「ついで修正」）→ 削除を差し戻しで指示（残す価値があれば issue 候補として承認フローへ）
- [ ] risk-modeling で「今回対応しない」と判断した項目に手を出していないか（判断を覆すなら理由の更新が必要）
- [ ] 途中で増えた仕様（会話中に膨らんだ要件）が完了条件チェックリストに反映されないまま実装されていないか
- [ ] 未検証のまま「完了」に分類された項目はないか
- [ ] 記憶適合起動判定行（[review-angles/README.md](review-angles/README.md)「条件起動系統」）が存在するか（レビューループ表を持つ PR のみ。`Tier: なし` で表を省略した PR は対象外）
- [ ] ヒット 1 件以上の判定行には、レビューループ記録表に記憶適合系統の行が対応して存在するか（判定したのに未起動、の検出）
- [ ] 判定行の検索語を `node scripts/agent-memory.js search` で再実行し、ヒット数が判定行の記載と一致するか（虚偽申告・検索失念の検出。不一致でも判定後の記憶状態の変化〔add の promote・supersede 等〕で説明できる場合は疑義としない。再実行が exit 非0 の場合は判定行が「実行不能」形式で記録されているかを確認する）
- [ ] 記憶適合系統の行に未解消の違反（`[衝突]`）が**無記録のまま**収束扱いになっていないか（人間判断で見送る場合は、更新候補への降格または見送り理由の記録があれば可）
- [ ] 記憶適合の更新候補（`[判断不足]`）・`[記憶不足]` 所見が PR 本文「残る制約・判断」へ転記されているか（人間判断への送達。転記が無いと収束後に消滅する）
- [ ] `incomplete`（`maxTurns` 到達等の未完了）を返したレビュアーの系統が、**所見ゼロ（収束）として記録されていない**か（[review-angles/README.md](review-angles/README.md)「実行設定」の incomplete 契約。未完了を収束と偽ると、確認していない範囲が「確認して所見ゼロ」に化ける）
- [ ] 外部レビューで**内部レビューが見逃した正当な新規所見**（✅）が出た PR で、実効 Tier 宣言行（`実効Tier: …`）または「加算不要と判断した理由」が記録されているか（[review-angles/README.md](review-angles/README.md)「実効 Tier の更新」。初期 Tier のまま無言で続行するのが最も起きやすい素通り）
- [ ] 実効 Tier へ加算された系統が、レビューループ記録で **fresh 起動**として実施されているか（同一レビュアーの継続だけで済ませていないか）

このドリフト監査は**前向き**（計画で「対応しない」と決めた項目に実装が触れていないか＝計画→diff 方向）である。対になる**後ろ向き**の監査（今 diff で加えた修正が過去の ⏭️ / 🔁 判断の前提を崩していないか＝diff→過去判断 方向）は [review-pr.md](review-pr.md) ステップ6.5「修正の波及セルフレビュー」が担う。両者は risk-modeling の想定ケース表を共通軸とする前向き／後ろ向きの対。

中間実行時はこの手順 4 のみでよい。検出したドリフトは即座に implementer / orchestrator に戻す。

### 5. 判定と差し戻し

- **⚠️ / ❌ が 1 つでもある** → 証拠表を添えて orchestrator（またはメインセッション）へ差し戻す。差し戻し理由は証拠表の該当行で完結させる（新たな解釈を加えない）。
- **全 ✅** → 証拠表を PR 本文（または作業メモ）に残し、[create-pr.md](create-pr.md) へ進んでよいと報告する。

evidence-check は**検証と差し戻しのみ**を行い、自分で修正しない（検証者が修正すると、その修正の検証者がいなくなる）。

## 機械的下限ゲート（自己言及的な穴を塞ぐ）

evidence-check は AI が実行するため、**この工程自体を「証拠表を作った ✅」と主張するだけで実体なく通せてしまう**（AIのチェックをAIが検証する再帰）。これを塞ぐため、AIレビューを最終ゲートにせず、その手前に**非AIの機械的下限ゲート**を置く。

- **コマンド:** `npm run check:artifacts`（`scripts/agent/check-artifacts.js`）。CI の `artifacts-gate` ジョブで PR 本文に対して必須実行する。Claude Code から **MCP ツール（`create_pull_request` / `update_pull_request`）経由**で PR を作成・本文更新する場合は、PreToolUse hook（`scripts/agent/hooks/check-pr-body.js`、登録: `.claude/settings.json`）が**PR を作る前に**同じ検査でブロックする（CI で赤にしてから直す往復を省く。hook は fail-open で、最終防衛線は CI 側）。`gh pr create` 等の CLI 経由や他エージェント（Codex / Gemini）は hook の対象外のため、[create-pr.md](create-pr.md) 手順 3.5 のローカル事前実行と CI が担保する。
- **機械が検証する範囲（存在・形式のみ）:**
  - コード変更 PR で「完了条件」「想定ケース」「既存実装調査」「証拠表」「レビューループ記録」セクションが PR 本文に**存在し非空**か（未作成のままの完了主張を不可能にする）。
  - 証拠表内で `✅` 判定の行・チェック済み `- [x]` 項目に**証拠ポインタが伴う**か（`N/A` や空を証拠として通さない。`[x] ビルド成功 — N/A` のような「未実施の成功偽装」を検出。skip 語で始まっても実ポインタがあれば通す — #395）。
  - レビューループ記録に**収束宣言**があるか（1周のみのレビューを収束と偽装できないようにする。正本: [pre-commit-review.md](pre-commit-review.md) ステップ6）。最終行は**閉じた受理文法**で判定する: 標準形式（`| 周回 | 新規所見 | 対応 |`）のヘッダから列を特定し、新規所見セル＝**数字のみ**（`0` / `0件`。説明文の併記は不可）、対応セル＝**「収束」単独**（上限超過時は「残所見: 内容」の非空列挙）。自由記述（「なし」「0件（…）」「未収束」等）は受理しない — 禁止パターンの列挙（ブロックリスト）では境界の穴が無限に残るため、受理側の文法を閉じて同クラスの偽装を構造的に塞ぐ。説明はセル外（周回セル・表外の本文）に書く。上限超過時の「残所見:」は**非空の列挙**を要する（空の `残所見:` は宣言として扱わない）。
  - コード変更 PR に**関連 issue 参照**（`#番号`）があるか（意図的に issue なしの場合は `関連issue: なし（理由）` を明記。closes 漏れによる stale-open issue の再発防止）。
- **機械が検証しない範囲（本工程＝人/別モデルに残る）:** 証拠が**真実か**、想定の網羅が妥当か、完了条件が要件を正しく写しているか。機械は floor（存在・形式）を保証し、内容の真偽は evidence-check（cross-model）が担う。
- **証拠の書式（機械が読める形）:** 証拠表は `- [x] {項目} — {証拠}`（em dash 区切り必須。区切りなしはラベル内のパスで自己証明できてしまうため不可）、またはテーブル `| 宣言 | 証拠 | 判定 |`。機械が落とすのは (a) `N/A`・`TODO`・`未実施` 等の**未実施宣言**（ポインタ併記でも不可）、(b) `確認済み`・`OK`・`目視`・`動作確認` 等の**宣言語で始まり**強い証拠ポインタ（拡張子付きパス / `npm run` 等コマンド）を伴わない証拠。宣言語で始まらない自由記述は形式上は通る（floor の限界）ため、その真偽は本工程（cross-model）が監査する。
- **例外:** artifact を出せない正当な事情がある場合のみ、PR 本文に `<!-- artifacts-check: skip (理由) -->` を明記する。理由なしの skip はゲートで落ちる。skip は黙って飛ばすのではなく **理由が diff に残る**（[docs/ai/README.md](../ai/README.md)「anti-skip rule」と同思想）。

このゲートは「未作成のままチェックを満たす」動きを機械的に不可能にするが、**証拠の中身が正しいことは保証しない**。真偽の検証は本工程（手順2〜4）で行う。
