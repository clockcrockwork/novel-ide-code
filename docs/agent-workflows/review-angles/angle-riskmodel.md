# risk-model 検証レビュー（観点別レビュアー）

> **Ground truth:** 実装計画・作業メモ・PR 本文の**想定ケース表**（[risk-modeling.md](../risk-modeling.md) の成果物）
> **Entry gate:** レビュー対象 diff と想定ケース表の両方を特定するまで所見作成に進まない（表が見つからない場合はそれ自体を ❌ 所見として返す）
> **Required artifacts:** 所見一覧（file/line/summary/failure_scenario＋下記4分類）
> **Verification gate:** 検出と分類のみ（修正・検証コマンドの実行は担わない）→ [docs/ai/rules/verification-gates.md](../../ai/rules/verification-gates.md)
> **Machine boundary:** この系統に**機械化済みの検出カテゴリは無い**（寄せ先の一覧: [docs/ai/rules/verification-gates.md](../../ai/rules/verification-gates.md)）。そのうえで、所見が機械で判定できると気づいたら **分類を「machine 化候補」にして寄せ先の欠落を名指しする**。**黙って落とさない** — 落とすと、ゲートが実際にはカバーしていない範囲の欠陥が machine からも AI からも見えなくなる。**寄せ先の gate が存在するのに検出できないときは、走査範囲・閾値・設定・CI/hook への配線の有無・exit code を返すかを根拠として添える。添えられないなら machine 化候補にせず、この系統の所見として扱う。寄せ先表に該当する検出カテゴリが無いときは、根拠を求めず「寄せ先の欠落」として machine 化候補にし、どの検出カテゴリが表に無いかを書く。** 正本: [docs/ai/rules/responsibility-boundary.md](../../ai/rules/responsibility-boundary.md)
> **Anti-skip:** [docs/ai/README.md](../../ai/README.md)「anti-skip rule」を参照。「表が古いので照合不能」で終えない — 照合不能自体を分類して返す
> **Cost note:** 表と diff の照合を飛ばすと、表が約束したガードの未実装（❌）と要求外実装（⚠️）が誰にも回収されずマージされる

あなたのアンカーは**想定ケース表**である。diff を先に読まず、まず表を読んで「この実装がしたはずの約束」を固定し、その約束が diff のどこで果たされているかを突き合わせる。

## 問い

- 表の約束（✅ 対応する、とされた各ケース）は diff のどこで果たされているか
- 表と diff の不整合はどれか

## 手順

1. 実装計画・作業メモ・PR 本文から想定ケース表を取得する
2. 表の各行について、対応する実装・テストの所在（ファイル:行）を diff から探す
3. 逆方向: diff の各変更について、根拠となる表の行を探す
4. [risk-modeling.md](../risk-modeling.md) の領域別チェック観点から、表にも diff にもないが必要なケースを導出する。diff が §非同期・競合の世代/シーケンス invariant 発火条件（**発火条件・記録書式・照合範囲の正本は同項目** — 公開・変更、または call site のみの追加・移動・削除）に該当するのに、正本の書式に従った call site 列挙が表に無い、または正本の定める照合範囲の grep で見つかる call site が列挙から漏れている場合（この型の失敗は diff 外の既存呼び出し元の更新漏れ — diff 内の照合だけでは検出できない）は、**❌（表の約束の前提欠落）** として返す。ルーティングは分類表 ❌ 行の前提欠落経路（表へ列挙を追記して再照合。実装/降格の2択ではない）。再照合の周回では、追記された列挙のうち「据え置き＋理由1行」が添えられた call site は ⏭️ 行と同様に前提の成立確認のみを行う（diff に変更が無いことを ❌ 約束未実装とはしない）
5. 全所見を下記4分類で返す

## 出力4分類（「表にないケース」の二義性の解決）

検出と分類までを行い、どちらに直すか（実装するか・表を直すか）は判断しない。不変条件は「表と実装が整合し、差分に理由が記録されている」こと。

| 分類 | 状態 | ルーティング |
|---|---|---|
| ✅ 整合 | 表の✅ケースに実装/テストの所在（ファイル:行）を指せる | なし |
| ❌ 約束未実装 | 表が約束したのに diff にない | 差し戻し（実装 or「対応しない」への降格＋理由）。**表の約束の前提欠落**（invariant の call site 列挙の不在・漏れ。手順4）の場合は実装/降格ではなく**表へ列挙を追記して再照合**の差し戻し |
| ⚠️ 表外実装 | diff にあるのに表にない | 作者＋orchestrator に二択を返す: 要求外なら削除（残す価値があれば issue 候補として承認フローへ）、必要なら表へ理由付き昇格 |
| ➕ 表の欠落 | 表にも diff にもないが領域別観点から必要と導出 | 表への追加提案のみ |

## 出力契約

所見は [finding-criteria.md](finding-criteria.md) の計上基準に従い「新規所見（修正要求。Med 以上）」と「参考（修正要求にしない。Low）」に分けて返す（同ファイルは全系統共通の正本で、観点の独立性とは無関係のため必ず読む）。

所見1件につき: `file` / `line` / `summary`（1文）/ `failure_scenario`（具体的な入力・状態 → 誤った結果）/ 上記4分類のいずれか（❌ のうち手順4の前提欠落に該当するものは **「❌（表の約束の前提欠落）」とサブラベル付きで返す** — 受け手はこのサブラベルで前提欠落経路〔追記して再照合〕を適用し、通常 ❌ の実装/降格2択を適用しない）。✅ 整合は件数と代表例のみでよい（全行の列挙は不要）。

- 検出と分類のみを行い、実装・修正は行わない
- 表の ⏭️（対応しない）行は前提の成立を1文で確認する（前提が崩れていれば ❌ 相当として報告する）
