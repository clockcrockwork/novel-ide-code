## 7系統・Tier の変遷

**運用性・状態遷移系統の追加**は、外部独立レビュアーとして使っていたモデル（Gemini）の退役に伴うギャップ分析から生まれた。退役前はこの外部レビューが state machine 系の欠陥（手順の実行主体不在・途中失敗からの復旧可能性等）を拾っていたため、退役後にレビュー系統として明示的に切り出し、Tier 表へ加算式で組み込んだ。

減算・清掃系統の追加と LIMIT 収束（review budget の前身）の経緯は `docs/planning/review-system-phase2-plan.md` を参照（本ファイルでは複製しない）。

旧「5系統」呼称（運用性・状態遷移、または減算・清掃を含まない構成）が本 README・関連 docs 中に残る場合があるが、現行は7系統である。

## 起動スケジューリング実装の経緯

以前の実装は内部フラグ `settled` の否定で段階（減算 → 本体 → 清掃）を選んでいた。判定ロジック自体は現行と同じだが、可観測性が乏しく、「まだ起動していない（保留）」と「起動条件を満たさないので充足扱い」を計画の出力から区別できなかった。ある改修で判定ロジックを変えずに、計画の各行へ `dirty` フラグを明示出力し、充足済みの義務を「保留」ではなく「充足」として報告するよう改めた（README.md「起動のスケジューリング」の `dirty` 判定はこの改修後の状態を指す）。

別の初期実装では、ある変更に対する減算系統の周回数が異常に伸びた実測（38 周まで到達）があった。原因は段階選択ロジックそのものではなく、次の3点だった。

- (a) 周回の数え方
- (b) 所見の分類・裁定の置き場所
- (c) 検出器が docs の1行変更でも減算トリガーを立てていたこと

(a)(b) は `docs/planning/review-memory-boundary.md` §3・§4 で境界を決め直して解消した。(c) は当時未解消で、検出器側の改善余地として残っている（README.md「起動のスケジューリング」の該当注記を参照）。
